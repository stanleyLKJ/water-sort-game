| UI / 场景交互修改 | `dotnet build`；Godot headless 或真实窗口验证；真实窗口未验收标记 `当前未确认` | 变更核心倒水规则，除非任务要求 | 在 `03_实现文档.md` 记录视觉/交互验收状态 |

未跟踪文档 diff 说明：

- 如果 `docs/` 是未跟踪目录，普通 `git diff -- docs/...` 可能无输出。
- 此时应以 `git status --short` 中的 `?? docs/...` 作为变更依据。
- 必要时可先使用 `git add -N docs/...` 让 Git 以 intent-to-add 方式显示 diff；如果不执行该操作，应在最终汇报中明确说明未跟踪文件无法通过普通 `git diff` 展示。

## 素材接入规则

`C:\Users\wuton\Documents\倒水小游戏\素材` 以及其所有子目录只作为素材收件箱 / staging input。

正式运行资源必须复制、重命名或清理后进入项目内 `res://assets/...` 或既有正式资源目录，再由场景和脚本通过 `res://` 路径引用。

禁止在任何 `.cs`、`.tscn`、`.tres`、`.res`、`.uid`、`.import` 或配置文件中写入运行期 Windows 绝对路径 `C:\Users\wuton\Documents\倒水小游戏\素材`。项目运行时、场景文件、脚本文件和资源文件不得直接引用素材收件箱。

后续所有美术素材接入流程固定为：

```text
external staging folder -> copy / rename / clean -> res://assets/... -> HomeGarden.tscn visual nodes -> manual visual acceptance
```

执行拆分：

1. `external staging folder`：只读取外部素材，不移动、不删除、不作为运行路径。
2. `copy / rename / clean`：复制到项目内，按正式 `flower_id`、slot、用途命名；必要时生成 cleaned 版本。
3. `res://assets/...`：所有运行资源进入项目正式目录，并由 Godot 导入。
4. `HomeGarden.tscn visual nodes`：主页花位素材必须在 `HomeGarden.tscn` 中建立或更新可编辑可视化节点，手动调整 anchors、offset、scale、`z_index` 和 texture；脚本后续只显示 / 隐藏已有节点。
5. `manual visual acceptance`：完成真实窗口或编辑器视觉验收；未完成时在 `03_实现文档.md` 标记 `当前未确认`。

如果素材存在透明外边、白线或杂点，可以在项目内生成 cleaned 版本；运行时只引用 cleaned 或正式命名版本。外部原始素材不删除、不移动，只复制。

第二阶段通用花素材目录规范：

```text
res://assets/flowers/{flower_id}/home_slots/{flower_id}_slot_01.png
res://assets/flowers/{flower_id}/home_slots/{flower_id}_slot_02.png
...
res://assets/flowers/{flower_id}/home_slots/{flower_id}_slot_07.png
res://assets/flowers/{flower_id}/select/{flower_id}_select.png
res://assets/flowers/{flower_id}/items/{flower_id}_seed.png
res://assets/flowers/{flower_id}/items/{flower_id}_potion.png
```

素材归属必须明确：

- 主页背景素材属于 `HomeGarden`，正式运行路径应在 `res://assets/home/backgrounds/`。
- 主页花位素材属于 `HomeGarden` 的已种植花显示，不是选花界面素材。
- 通关奖励道具素材属于 `HomeGarden` 的 `PendingPlanting` 点击后临时种植 / 追加动画，正式运行路径应在 `res://assets/flowers/{flower_id}/items/`，每个开放花需要 `{flower_id}_seed.png` 和 `{flower_id}_potion.png`。
- `assets/flowers/{flower_id}/items/` 不得与 `assets/flowers/{flower_id}/home_slots/` 混用；奖励道具图不能放进 `home_slots`，也不能作为已种植花位素材。
- `assets/flowers/{flower_id}/items/` 不得与 `assets/flowers/{flower_id}/select/` 混用；奖励道具图不能放进 `select`，也不能修改 `FlowerSelect` 的 `select` 读取规则。
- `GameScene` 的 `CauldronView` 和 `HomeGardenView` 都应使用正式奖励道具路径 `res://assets/flowers/{flower_id}/items/{flower_id}_seed.png` 与 `..._potion.png`；缺失时 warning 并隐藏对应图片，不得崩溃。`RunSessionState` 不得保存这些图片路径。
- `CauldronView` 只负责在通关前展示本局目标花的种子 / 药剂图片、文字和“种植”按钮；奖励层默认停留 3 秒后自动继续，点击“种植”按钮时立即跳过剩余等待。
- `CauldronView` 的自动继续和按钮继续必须共用一次性完成入口，避免重复触发 `GameManager.LevelCompleted`。
- `GameScene` / `CauldronView` 不直接写 `RunSessionState`，不操作 `HomeGarden`；奖励展示完成后仍只通过 `GameManager.LevelCompleted` 交给 `MainFlowController`。
- `PendingPlanting` 状态下，主页不得常驻展示种子 / 药剂静态奖励面板；只有点击可操作数字圆圈后，种子 / 药剂图标才临时显示并播放动画。
- 奖励道具图片缺失时，`HomeGardenView` 只能 warning 并跳过对应图标动画，不得崩溃。
- 每一种花都需要 7 个主页固定位置贴图，因为同一种花放在不同花位时，位置、透视、缩放和遮挡可能不同。
- 主页花位素材接入必须同时完成 `HomeGarden.tscn` 场景可视化贴图节点接入，不能只复制 PNG 并依赖运行时动态加载。
- 现有 `PinkRoseSlot_01` 到 `PinkRoseSlot_07` 是历史节点名，当前语义是 7 个固定主页花位。每个 slot 下应保留 slot 锚点 / 点击热区，并建立花种视觉容器，例如 `FlowerVisualRoot`。
- 已确认正式花种应在每个 slot 的视觉容器下拥有独立 `TextureRect` 节点，例如 `PinkRoseTexture`、`YellowRoseTexture`。不同花种节点允许拥有不同 anchors、offset、scale、`z_index`。
- 主页素材的位置、缩放、anchors、offset、`z_index`、遮挡层级和 texture 引用均以 `HomeGarden.tscn` 中保存的可视化节点为准；不得用代码作为主页素材布局或贴图来源的权威。
- 目标花选择素材属于 `FlowerSelect`，不是主页花位素材。
- 每种花至少需要 1 张选择页展示图或卡片图。
- `HomeGarden` 的主页花位素材和 `FlowerSelect` 的选择页展示素材不能混用。

第二阶段花素材接入流程固定为：

```text
external staging folder
-> copy / rename / clean
-> res://assets/flowers/{flower_id}/home_slots/
-> 在 HomeGarden.tscn 中建立或更新可视化节点
-> 手动调整 anchors / offset / scale / z_index / texture
-> HomeGardenView 只负责显示 / 隐藏已有节点
-> 人工视觉验收
```

运行时边界：

- `RunSessionState` 仍只保存 `flower_id` 和 slot batch，不保存图片路径、节点路径、Godot 节点引用或本地存档路径。
- `HomeGardenView` 根据 `RunSessionState` 的 slot batch 显示对应已有节点，并隐藏同一 slot 下不该显示的其他节点。
- `HomeGardenView` 不得动态创建主页花图节点；不得动态设置主页花位 texture；不得用代码设置主页花图 position、scale、offset、anchors 或 `z_index`。
- 节点缺失时，后续代码实现应输出 warning 并隐藏该主页表现，或标记为待补节点；不得自动从 `res://assets/flowers/{flower_id}/home_slots/` 或 `res://assets/flowers/combinations/{combo_key}/home_slots/` 动态补图。
- `res://assets/flowers/{flower_id}/home_slots/` 和组合 `home_slots` 目录可以作为素材归档和场景节点 texture 来源，但不允许作为 `HomeGarden` 正式运行时 fallback 策略。
- `FlowerSelect` 仍然只读取 `select` 目录，不能使用 `home_slots` 作为选择页素材。
- 本规则优先作用于 `HomeGarden`；`FlowerSelect` 是否也改成纯可视化，后续单独确认。

## 核心模块职责（执行侧摘要）

本节只记录开发时需要快速遵守的职责摘要。完整模块职责、数据流和禁止越界边界以 `docs/04_架构文档.md` 为准。

### 数据层

数据层只保存真实游戏状态，不写表现逻辑，不直接操作 Godot 节点。

包括：

- `WaterColor`
- `WaterLayer`
- `BottleData`
- `BagData / CauldronProgressData`（`BagData` 为 `[DEBT]` 历史命名兼容层）
- `GameState`
- `PourPlan`
- `PourResult`

核心约定：

- 真实颜色存在数据层。
- 是否已揭示存在数据层。
- 是否已收集存在数据层。
- 胜利状态存在数据层。

### 系统层

系统层负责游戏规则、流程调度和状态变更。

包括：

- `GameManager`
- `PourSystem`
- `BagSystem / CauldronProgress`（`BagSystem` 为 `[DEBT]` 历史命名兼容层）
- `LevelGenerator`
- `UIManager`

系统层可以读取和修改数据层，但不应把复杂规则散落到表现层。

### 表现层

表现层负责显示、点击输入和反馈动画。

包括：

- `BottleView`
- `BagSlotView / CauldronProgressView`（`BagSlotView` 为 `[DEBT]` 历史显示文件，当前正式视觉使用 `CauldronView`）
- UI 节点脚本

表现层不判断倒水规则，不判断胜利，不直接生成关卡。

## 关键类职责（执行侧摘要）

本节用于执行任务前快速定位相关类；类职责若与 `docs/04_架构文档.md` 的状态归属表或禁止越界职责冲突，以 `docs/04_架构文档.md` 为准。

### GameManager

负责：

- 初始化游戏。
- 持有或管理 `GameState`。
- 接收水瓶点击事件。
- 管理选中、取消选中、尝试倒水流程。
- 调用 `PourSystem` 执行倒水规则。
- 调用 `BagSystem / CauldronProgress` 执行自动收集并更新炼药锅调试进度。
- 调用 `UIManager` 显示提示、胜利弹窗。
- 刷新全部视图。
- 重开游戏。

不负责：

- 不直接写倒水规则细节。
- 不直接判断满瓶同色细节。
- 不在表现节点中保存真实游戏状态。

### PourSystem

负责：

- 判断源瓶和目标瓶是否合法。
- 判断目标是否为空或顶部同色。
- 计算本次可倒出的已揭示顶部连续同色层数。
- 按目标剩余容量计算实际倒入层数。
- 执行数据层面的倒水。
- 倒水成功后只解锁源瓶新的顶部层。

推荐保持两阶段接口：

- `TryCreatePourPlan(source, target)`：只判断并返回计划，不修改数据。
- `ExecutePour(plan, state)`：根据计划修改数据。

### BagSystem / CauldronProgress

负责：

- 判断水瓶是否满瓶同色。
- 将完成水瓶标记为已收集。
- 增加对应颜色的炼药锅调试进度计数。
- 返回被收集水瓶 ID，方便表现层隐藏或播放反馈。

注意：`BagSystem`、`BagData`、`BagSlotView` 是 `[DEBT]` 历史命名兼容层。当前正式语义是炼药锅调试进度收集，文档中推荐写作 `BagSystem / CauldronProgress` 或 `Bag* 历史命名兼容层`；旧 `FlowerPotSystem` / 花盆收集区只应出现在 `[DEPRECATED]` / `[HISTORICAL]` 说明中。

### LevelGenerator

负责：

- 生成或加载关卡数据。
- 保证 4 种颜色每种 4 层。
- 保证使用 6 个水瓶。
- 保留 1 到 2 个空瓶。
- 设置非空瓶顶层为已揭示，其他层为问号未揭示。

执行顺序建议：

1. 先保留固定测试关卡，保证玩法稳定。
2. 再做简单随机洗牌，并标记可能无解。
3. 最后升级为从完成状态反向打乱的可解关卡。

### UIManager

负责：

- 绑定重开按钮。
- 显示或隐藏胜利弹窗。
- 显示“不能倒入”提示。
- 控制提示文字自动消失。

不负责：

- 不生成关卡。
- 不判断胜利。
- 不执行倒水。

### BottleView

负责：

- 处理水瓶点击输入。
- 通知 `GameManager` 哪个水瓶被点击。
- 根据 `BottleData` 刷新真实颜色层、问号层、空层、收集隐藏状态。
- 显示选中上移效果。
- 显示无效倒水摇晃反馈。
- 显示瓶内水位的连续填充、瓶身内部裁剪和顶部轻微波浪。
- 以临时表现快照播放源瓶水位下降、目标瓶水位上升动画。
- 显示本次 `PourPlan.Color` 对应颜色的柔和水流。

不负责：

- 不判断是否能倒。
- 不决定倒几层。
- 不判断通关。
- 不保存唯一真实游戏状态。

## 倒水动画和水位表现执行边界

倒水动画属于表现层升级，不改变 `PourSystem`、`BottleData`、`WaterLayer`、`PourPlan`、`PourResult` 的核心规则和数据语义。

合法倒水执行顺序应保持：

1. `GameManager` 通过 `PourSystem.TryCreatePourPlan(source, target)` 取得倒水计划。
2. `GameManager` 锁定输入并清除选中态。
3. `BottleView` 播放源瓶移动、倾斜、水流、水位下降和目标水位上升的表现动画。
4. 动画过程中由 `GameManager` 调用 `PourSystem.ExecutePour(plan, state)` 修改真实数据。
5. 动画结束后刷新所有瓶子和炼药锅进度视图。
6. 刷新后执行自动收集结果展示、炼药锅进度表现和通关奖励展示判断。

实现要求：

- 水流节点可以是全局 `Line2D`，但应由表现层控制显示与隐藏。
- 水流显示/隐藏应优先由 `transfer_committed` 或 `pouring_state_changed` 这类领域信号驱动；在当前 C# 实现中对应 `GameManager.TransferCommitted` 和 `GameManager.PouringStateChanged`。
- 水流至少包含 3 个点，建议 4 个点形成轻微弧线。
- 水流必须启用抗锯齿，并通过渐隐颜色或宽度曲线柔化头尾。
- 当 `moved <= EPSILON` 时，表现层不得显示水流。
- 当状态进入 `Idle`、`Cancelled` 或 `Blocked` 时，表现层必须立即隐藏水流。
- `PourFX` / `PourFxView` 只能读取提交结果中的源点、目标点、颜色和移动量，不得修改 `BottleData`、`GameState` 或倒水计划。
- 水位过渡可以使用表现层临时快照，但真实状态仍以数据层为准。
- 表现层临时快照不得参与规则判断，不得替代 `GameState`。
- 瓶内水层应通过裁剪区域或等效实现限制在瓶身内部，问号黑色层也必须受同一内部区域约束。
- 水层几何应连续贴合，避免层与层之间出现固定空隙。
- 顶部水面可使用轻微波浪，但不得影响层数、颜色和问号规则。
- 非法倒水反馈、自动收集、通关奖励展示和重开流程必须保持稳定；旧胜利弹窗不得替代当前关卡内种子 x1 + 药剂 x1 奖励展示。

## 点击交互状态机

建议使用简单状态机管理点击：

| 状态 | 含义 |
| --- | --- |
| Idle | 没有选中任何瓶子 |
| BottleSelected | 已选中一个源瓶 |
| Resolving | 正在执行倒水或反馈，短暂锁输入 |
| Win | 游戏胜利，停止水瓶输入 |

第一版可用 `SelectedBottleId` 和 `IsGameOver` 实现简化状态，但行为必须满足：

- Idle：点击非空、未收集瓶子后选中它。
- Idle：点击空瓶不应选为源瓶。
- BottleSelected：点击同一个瓶子取消选中。
- BottleSelected：点击另一个瓶子尝试倒水。
- Resolving：忽略连点，避免状态错乱。
- Win：忽略水瓶点击，只允许重开。

## 倒水规则实现原则

倒水必须满足：

- 源瓶非空。
- 源瓶和目标瓶不是同一个。
- 源瓶和目标瓶都未被收集。
- 目标瓶未满。
- 源瓶顶部层已揭示。
- 目标瓶为空，或目标瓶顶部真实颜色等于源瓶顶部真实颜色。

计算本次倒出层数时，只统计源瓶顶部已揭示的连续同色层。

实际倒入层数：

```text
min(源瓶顶部已揭示连续同色层数, 目标瓶剩余容量)
```

倒入目标瓶的新水层必须设为已揭示，因为玩家刚刚看到它被倒进去。

## 问号层实现原则

- 数据层中每层水都提前保存真实颜色。
- `IsRevealed` 控制该层是否显示真实颜色。
- 初始每个非空瓶只揭示当前顶部层。
- 成功倒水后，只尝试揭示源瓶新的顶部层。
- 新揭示层不参与本次已经生成的 `PourPlan`。
- 已揭示层不能重新变回问号。

## 自动收集实现原则

收集条件：

- 水瓶未被收集。
- 水瓶层数等于容量。
- 所有层真实颜色相同。

收集后：

- `BottleData.IsCollected = true`。
- 对应颜色 `BagData.CollectedCount` / `CauldronProgress` 计数增加。
- 水瓶视图隐藏或播放收集反馈。
- 该水瓶不再可点击，也不能再参与倒水。

建议每次成功倒水后检查所有水瓶。第一版只有 6 个水瓶，全量检查最简单稳定。

## 炼药锅替换执行边界

旧 `GameScene` 顶部四个花盆替换为炼药锅调试表现时，执行边界如下：

- `GameScene` 顶部四个 `BagSlot` / 花盆节点不得继续作为当前正式视觉表现；可以保留为历史节点，但必须隐藏或从正式显示链路解绑。
- 新正式表现应使用 `CauldronRoot` / `CauldronView` / `CauldronSprite` / `CauldronProgressRoot` 等炼药锅语义节点。
- `BagSystem` / `BagData` 可作为历史兼容命名保留，当前语义是“炼药锅调试进度收集逻辑”；本次不强制重命名或删除 `Bag*` 文件。
- 满瓶同色收集时，表现层应播放完成瓶从当前位置飞向炼药锅的 Tween 动画；动画完成后再隐藏该瓶或进入已收集状态。
- 全部颜色完成后，`GameScene` 先展示本局目标花对应的“种子 x1 + 药剂 x1”奖励层，再发出 `GameManager.LevelCompleted` 交给 `MainFlowController`；当前第三阶段出口为写入 `SaveData` 仓库库存并回到 `HomeGarden`。
- `GameScene` 不自行选择奖励花；目标花仍来自 `RunSessionState.SelectedFlowerId` / `MainFlowController` 当前选择。
- 本任务不得顺手重构 `PourSystem`、`BottleData`、`WaterLayer`、`PourPlan`、`PourResult` 的核心规则和数据语义；如遇编译必要的小范围适配，必须在实现文档和最终汇报说明原因。

## 第三阶段种植纠偏执行规则

当前第三阶段第四批二次纠偏后，`PlantingPage` 不得作为正式种植入口选花页；“种植页面”按钮必须直接让 `HomeGarden` 进入先选位置的种植状态：

1. `HomeGarden` 点击“种植页面”后，不加载 `PlantingPage`，仍停留在 `HomeGarden`。
2. `RunSessionState.IsWarehousePlantingMode` 或等价字段表示“等待玩家选择 slot”，不得要求 `PendingPlantingFlowerId` 已有值；`PendingPlanting` 若继续保留，只能作为兼容旧待种植流程字段。
3. `HomeGardenView` 在该模式下只显示可操作 1-7 数字圆圈：空 slot 只要仓库中至少有一种可种花就显示；已有花位只要仓库中至少有一种当前 slot 尚未包含的可种花就显示。

- `MainFlowController` 负责 `HomeGarden -> FlowerSelect -> LevelSelect -> GameScene -> HomeGarden` 的外层切换、奖励生成和种植状态提交。

- 单花也是组合的一种；单花和多花组合都应在 `HomeGarden.tscn` 中拥有对应可视化节点。
- `res://assets/flowers/combinations/{combo_key}/home_slots/{combo_key}_slot_01.png` 到 `slot_07.png` 可以作为素材归档路径和场景节点 texture 来源，但不允许作为正式运行时动态加载 fallback。
- 多花组合节点缺失时，后续代码实现只能 warning / 隐藏 / 标记待补，不得崩溃，也不得把多个单花素材临时叠加或动态补图作为正式表现。

第二阶段验收标准：

- 游戏启动后首先显示 `HomeGarden`。
- `HomeGarden` 的“选择关卡”按钮隐藏且禁用，“开始游戏”仍可用。
- “开始游戏”进入 `FlowerSelect`；若 `PendingPlanting` 未完成，停留主页并提示。
- `FlowerSelect` 显示 6 格，只有 `pink_rose`、`yellow_rose`、`lavender` 可进入 `LevelSelect`。
- 点击 `flower_04` 到 `flower_06` 只提示“该花将在后续版本开放”。
- 所选开放花进入 `LevelSelect` 后显示 7 关；第 1 关默认可玩；已完成和未解锁关不可进入。
- 通关第 1 关后，第 1 关锁定，第 2 关解锁；不同花的进度互相独立。
- 通关后生成对应花的 `PendingPlanting`，不进入 `RewardFlower`。
- 空位可种植本次奖励花；已有但不含本次奖励花的位置可追加；已含本次奖励花的位置不可追加。
- 追加后花位保存为排序稳定的组合批次，例如 `pink_rose+yellow_rose`。
- 缺少多花组合可视化节点时 warning / 隐藏 / 标记待补，不崩溃，不动态补图。
- 同一花出现在 7 个不同位置后，`FlowerSelect` 中该花灰态并提示“该花已种满，请选择其他花”。
- 第一版倒水规则、问号层、自动收集、胜利判断、重开功能不被破坏。
- `GameScene` 中炼药锅进度格应使用可区分的柔和红 / 蓝 / 黄 / 绿魔法色，不得在完成后全部显示为黄色。
- `GameScene` 的提示文字、胜利弹窗、炼药锅奖励文本和调试按钮文字应在手机竖屏下清楚可读；低对比白字优先用 `LabelSettings` / theme override 描边、深色文字或半透明深色底板处理。
- 主流程进入 `GameScene` 后点击退出应返回当前 `LevelSelect`；`PendingPlanting`、`HasSeed`、`HasPotion` 保持 false，当前关卡完成数不增加，再次点击当前可玩关仍能进入 `GameScene`。
- `RestartButton` 原有重开行为必须保持，不得被退出按钮替换或复用为外层返回。
- 修改代码后必须运行 `dotnet build`；流程 / UI 改动必须运行 Godot headless 或可行 smoke；真实窗口未验收时必须在 `03_实现文档.md` 标记当前未确认。

## 每次 Codex 执行任务前后的流程

执行前：

1. 先读取本次用户消息、附件和粘贴文本，确认本次明确任务是什么。
2. 阅读 `docs/01_需求文档.md`，确认本次任务对应的需求是否存在或是否与需求冲突。
3. 阅读 `docs/02_执行文档.md`，确认应该按什么工程边界实现。
4. 阅读 `docs/03_实现文档.md`，确认当前项目已经做到哪一步。
5. 阅读 `docs/04_架构文档.md`，确认架构认知、模块边界、场景关系和数据流。
6. 用 `git status --short` 确认工作区状态。
7. 识别已有未提交改动，避免覆盖用户改动。
8. 明确本次任务只改哪些文件。
9. 如果涉及玩法规则，先阅读对应核心代码。

重要约束：

- `docs/03_实现文档.md` 中的“下一步建议”只作为背景，不是默认任务来源。
- 如果用户消息或附件中存在明确任务，必须优先执行该任务；不能跳过附件内容后自行选择“下一步建议”。
- 如果本次明确任务与四份权威文档冲突，先指出冲突并按用户本次确认后的方向执行。
- 如果用户提出新的推进方向、需求或任务，且四份权威文档尚未记录，执行前或执行中必须同步更新文档；不能只改代码或只在对话中确认。
- 新增正式需求必须更新 `docs/01_需求文档.md`；新增执行约束、工程规则或验收方式必须更新 `docs/02_执行文档.md`；任何执行结果、临时实现、当前状态变化和未确认事项必须更新 `docs/03_实现文档.md`；如果涉及架构变化、模块边界、场景关系、数据流或状态管理变化，必须更新 `docs/04_架构文档.md`。
- 如果新增内容只是临时实验，也必须在 `docs/03_实现文档.md` 明确标记为临时实现，并说明是否已经纳入正式需求。

执行中：

- 小步修改，避免一次性大改。
- 对核心规则改动优先保持数据层、系统层、表现层边界。
- 每个阶段完成后尽量能从磁盘状态继续，不把关键进展只保存在对话中。

执行后：

1. 运行必要验证，至少包括 `dotnet build`，除非本次只改文档且无代码影响。
2. 玩法或 UI 改动需要用 Godot 真实窗口验证。
3. 按本次变更性质同步更新 `docs/01_需求文档.md`、`docs/02_执行文档.md`、`docs/03_实现文档.md`；涉及架构变化、模块边界、场景关系、数据流或状态管理变化时，同步更新 `docs/04_架构文档.md`。
4. 更新 `docs/03_实现文档.md` 的当前状态或执行记录。
5. 用 `git status --short` 汇报变更范围。

## 验收方式

文档类任务：

- 四份权威文档存在。
- 旧文档已移入 `docs/archive/`。
- 新文档顶部包含权威声明。
- `docs/04_架构文档.md` 已存在，并在顶部声明其为架构权威文档。
- `docs/03_实现文档.md` 已记录本次执行。

美术规范信息图任务：

- 输出文件应放在 `docs/` 下，优先使用可直接打开、可打印、可截图的自包含 HTML/CSS/SVG。
- 标题必须使用《瓶装液体表现制作与验收规范（专业版）》。
- 内容必须按“结构、遮罩、液位透视、出水路径、动画同步、材质、动态、风格统一、验收与回退”的顺序组织。
- 图文必须一致，右侧示意图应明确标注瓶壁厚度、可见液体区域、正确/错误遮罩、起点、终点和重力方向。
- 底部必须包含推荐执行顺序和专业判断框。
- 中文必须完整、准确、可读，不得出现半截句或含糊表达。
- 该任务只生成规范交付物时，不需要运行 `dotnet build`；但需要检查 HTML 文件存在、关键文案存在，并尽量完成一次本地渲染或截图验证。

代码类任务：

- `dotnet build` 通过。
- 第一阶段或倒水关卡内部任务：运行 `GameScene.tscn` 无启动错误。
- 第二阶段流程任务：运行项目实际启动入口 `main.tscn` 无启动错误，并首先进入花园主页。
- 点击源瓶后能选中上移。
- 合法倒水成功更新水层。
- 合法倒水时源瓶会移动并倾斜，动画期间输入保持锁定。
- 合法倒水时水流颜色与 `PourPlan.Color` 一致，并呈现柔和弧线而不是单条硬直线。
- 合法倒水时源瓶水位下降、目标瓶水位上升有过渡动画。
- 水层和问号黑色层显示在瓶身内部，不明显越界。
- 水层视觉连续填充，不再像 4 个分离硬块。
- 非法倒水显示“不能倒入”并摇晃目标瓶。
- 问号层只在倒走后逐层解锁。
- 新解锁同色层不会在同一次操作继续倒出。
- 满瓶同色后自动投入炼药锅 / 更新炼药锅调试进度。
- 收集后水瓶不再参与倒水。
- 4 个完成瓶收集后弹出胜利提示。
- 主按钮和胜利弹窗按钮都能重开。

按美术规范优化表现层任务：

- 优先修改 `BottleView`、`PourFxView` 等表现层文件，除非明确需要，不修改 `PourSystem`、数据模型和核心规则。
- 瓶内裁剪区域需要贴合当前瓶子素材，覆盖瓶身内腔和瓶底弧线，避开瓶口外轮廓。
- 水层应连续填充，层间用轻量高光或软边界区分，不使用明显分离硬块。
- 问号层必须与真实颜色层使用同一瓶内裁剪区域。
- 水流起点应使用源瓶倾斜后的 `PourPoint`，终点使用目标瓶接收点。
- 水流路径应使用多点弧线，并体现重力下坠、头尾收束、高光和末端滴落。
- 修改后必须运行 `dotnet build`；能定位 Godot 可执行文件时，还应执行 headless 启动冒烟验证。
- 若未完成真实窗口点击视觉验收，必须在 `docs/03_实现文档.md` 中记录为未确认。

液体遮罩方案执行规则：

- 不再用硬编码多边形宽度去拟合瓶身内腔作为主要方案。
- 水层几何应保持简单，优先使用水平矩形或近似矩形，瓶身形状由 mask 裁剪。
- 遮罩资源统一放在 `assets/bottles/bottle_liquid_mask.png`，其透明区域表示不可见，白色不透明区域表示可见液体区域。
- `BottleView` 应能在资源尚未生成 `.import` 时通过文件路径直接加载 mask，避免 headless 启动时因新 PNG 未导入失败。
- 玻璃瓶前景层必须位于液体层之上。
- 如后续提供正式 `BottleBack.png` / `BottleFront.png`，表现层应优先使用分层素材替换当前完整瓶图过渡方案。
