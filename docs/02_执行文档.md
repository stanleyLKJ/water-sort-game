# 02 执行文档

本项目当前以 01_需求文档.md、02_执行文档.md、03_实现文档.md、04_架构文档.md 四份权威文档为准，archive 中旧文档不再作为执行依据。

## 执行规则编号体系

| 规则 ID | 规则摘要 | 当前要求 |
| --- | --- | --- |
| EXE-GIT-001 | 执行前检查 git 状态 | 每次任务执行前运行 `git status --short`，识别既有未提交改动并避免覆盖 |
| EXE-DOC-001 | 需求变更必须同步文档 | 新增或变更需求时同步更新四份权威文档中的对应职责部分 |
| EXE-BUILD-001 | 代码修改后必须运行 `dotnet build` | 只改文档时不需要；修改 `.cs` 或影响 C# 编译时必须运行 |
| EXE-GODOT-001 | UI / 场景 / 交互修改后需要 Godot 验证 | 场景、UI、流程和交互变更需要 headless 或真实窗口验证；真实窗口未验收必须标记未确认 |
| EXE-ASSET-001 | 素材不得直接引用外部 staging 路径 | 运行路径不得引用 `素材/` 或 Windows 绝对 staging 路径 |
| EXE-ASSET-002 | 正式资源必须复制到 `res://assets` | 外部素材需复制、重命名、清理后进入项目正式资源目录，再由场景/脚本引用 |
| EXE-ARCH-001 | 架构边界变更必须更新架构文档 | 模块职责、状态归属、场景关系或数据流变化时更新 `04_架构文档.md` |

| 流程调整 | 同步 `01_需求文档.md` 当前正式流程、`02_执行文档.md` 验收规则、`03_实现文档.md` 当前状态、`04_架构文档.md` 流程契约 | 保留旧流程为当前正式入口 | 明确旧流程是否历史遗留、当前未确认或已废弃 |

未跟踪文档 diff 说明：

- 如果 `docs/` 是未跟踪目录，普通 `git diff -- docs/...` 可能无输出。
- 此时应以 `git status --short` 中的 `?? docs/...` 作为变更依据。
- 必要时可先使用 `git add -N docs/...` 让 Git 以 intent-to-add 方式显示 diff；如果不执行该操作，应在最终汇报中明确说明未跟踪文件无法通过普通 `git diff` 展示。

## 素材接入规则

`C:\Users\wuton\Documents\倒水小游戏\素材` 以及其所有子目录只作为素材收件箱 / staging input。

正式运行资源必须复制、重命名或清理后进入项目内 `res://assets/...` 或既有正式资源目录，再由场景和脚本通过 `res://` 路径引用。

禁止在任何 `.cs`、`.tscn`、`.tres`、`.res`、`.uid`、`.import` 或配置文件中写入运行期 Windows 绝对路径 `C:\Users\wuton\Documents\倒水小游戏\素材`。项目运行时、场景文件、脚本文件和资源文件不得直接引用素材收件箱。

后续所有美术素材接入流程固定为：

```text
external staging folder -> copy / rename / clean -> res://assets/... -> scene visual nodes + script res:// reference -> manual visual acceptance
```

执行拆分：

1. `external staging folder`：只读取外部素材，不移动、不删除、不作为运行路径。
2. `copy / rename / clean`：复制到项目内，按正式 `flower_id`、slot、用途命名；必要时生成 cleaned 版本。
3. `res://assets/...`：所有运行资源进入项目正式目录，并由 Godot 导入。
4. `scene visual nodes + script res:// reference`：场景节点和脚本只引用 `res://` 路径；主页花位素材还需要可编辑视觉节点。
5. `manual visual acceptance`：完成真实窗口或编辑器视觉验收；未完成时在 `03_实现文档.md` 标记 `当前未确认`。

如果素材存在透明外边、白线或杂点，可以在项目内生成 cleaned 版本；运行时只引用 cleaned 或正式命名版本。外部原始素材不删除、不移动，只复制。

第二阶段通用花素材目录规范：

```text

res://assets/flowers/{flower_id}/home_slots/{flower_id}_slot_02.png
...
res://assets/flowers/{flower_id}/home_slots/{flower_id}_slot_07.png
res://assets/flowers/{flower_id}/select/{flower_id}_select.png
```

素材归属必须明确：

## 核心模块职责

### 数据层

数据层只保存真实游戏状态，不写表现逻辑，不直接操作 Godot 节点。

包括：

- `WaterColor`
- `WaterLayer`
- `BottleData`
- `BagData/FlowerPotData`
- `GameState`
- `PourPlan`
- `PourResult`

核心约定：

- 真实颜色存在数据层。
- 是否已揭示存在数据层。
- 是否已收集存在数据层。
- 胜利状态存在数据层。

### 系统层

系统层负责游戏规则、流程调度和状态变更。

包括：

- `GameManager`
- `PourSystem`
- `BagSystem/FlowerPotSystem`
- `LevelGenerator`
- `UIManager`

系统层可以读取和修改数据层，但不应把复杂规则散落到表现层。

### 表现层

表现层负责显示、点击输入和反馈动画。

包括：

- `BottleView`
- `BagSlotView/FlowerPotSlotView`
- UI 节点脚本

表现层不判断倒水规则，不判断胜利，不直接生成关卡。

## 关键类职责

### GameManager

负责：

- 初始化游戏。
- 持有或管理 `GameState`。
- 接收水瓶点击事件。
- 管理选中、取消选中、尝试倒水流程。
- 调用 `PourSystem` 执行倒水规则。
- 调用 `BagSystem/FlowerPotSystem` 执行自动收集。
- 调用 `UIManager` 显示提示、胜利弹窗。
- 刷新全部视图。
- 重开游戏。

不负责：

- 不直接写倒水规则细节。
- 不直接判断满瓶同色细节。
- 不在表现节点中保存真实游戏状态。

### PourSystem

负责：

- 判断源瓶和目标瓶是否合法。
- 判断目标是否为空或顶部同色。
- 计算本次可倒出的已揭示顶部连续同色层数。
- 按目标剩余容量计算实际倒入层数。
- 执行数据层面的倒水。
- 倒水成功后只解锁源瓶新的顶部层。

推荐保持两阶段接口：

- `TryCreatePourPlan(source, target)`：只判断并返回计划，不修改数据。
- `ExecutePour(plan, state)`：根据计划修改数据。

### BagSystem/FlowerPotSystem

负责：

- 判断水瓶是否满瓶同色。
- 将完成水瓶标记为已收集。
- 增加对应颜色花盆的收集数量。
- 返回被收集水瓶 ID，方便表现层隐藏或播放反馈。

注意：历史代码中的 `BagSystem` 语义等同于新需求中的 `FlowerPotSystem`。

### LevelGenerator

负责：

- 生成或加载关卡数据。
- 保证 4 种颜色每种 4 层。
- 保证使用 6 个水瓶。
- 保留 1 到 2 个空瓶。
- 设置非空瓶顶层为已揭示，其他层为问号未揭示。

执行顺序建议：

1. 先保留固定测试关卡，保证玩法稳定。
2. 再做简单随机洗牌，并标记可能无解。
3. 最后升级为从完成状态反向打乱的可解关卡。

### UIManager

负责：

- 绑定重开按钮。
- 显示或隐藏胜利弹窗。
- 显示“不能倒入”提示。
- 控制提示文字自动消失。

不负责：

- 不生成关卡。
- 不判断胜利。
- 不执行倒水。

### BottleView

负责：

- 处理水瓶点击输入。
- 通知 `GameManager` 哪个水瓶被点击。
- 根据 `BottleData` 刷新真实颜色层、问号层、空层、收集隐藏状态。
- 显示选中上移效果。
- 显示无效倒水摇晃反馈。
- 显示瓶内水位的连续填充、瓶身内部裁剪和顶部轻微波浪。
- 以临时表现快照播放源瓶水位下降、目标瓶水位上升动画。
- 显示本次 `PourPlan.Color` 对应颜色的柔和水流。

不负责：

- 不判断是否能倒。
- 不决定倒几层。
- 不判断通关。
- 不保存唯一真实游戏状态。

## 倒水动画和水位表现执行边界

倒水动画属于表现层升级，不改变 `PourSystem`、`BottleData`、`WaterLayer`、`PourPlan`、`PourResult` 的核心规则和数据语义。

合法倒水执行顺序应保持：

1. `GameManager` 通过 `PourSystem.TryCreatePourPlan(source, target)` 取得倒水计划。
2. `GameManager` 锁定输入并清除选中态。
3. `BottleView` 播放源瓶移动、倾斜、水流、水位下降和目标水位上升的表现动画。
4. 动画过程中由 `GameManager` 调用 `PourSystem.ExecutePour(plan, state)` 修改真实数据。
5. 动画结束后刷新所有瓶子和花盆视图。
6. 刷新后执行自动收集结果展示和胜利弹窗判断。

实现要求：

- 水流节点可以是全局 `Line2D`，但应由表现层控制显示与隐藏。
- 水流显示/隐藏应优先由 `transfer_committed` 或 `pouring_state_changed` 这类领域信号驱动；在当前 C# 实现中对应 `GameManager.TransferCommitted` 和 `GameManager.PouringStateChanged`。
- 水流至少包含 3 个点，建议 4 个点形成轻微弧线。
- 水流必须启用抗锯齿，并通过渐隐颜色或宽度曲线柔化头尾。
- 当 `moved <= EPSILON` 时，表现层不得显示水流。
- 当状态进入 `Idle`、`Cancelled` 或 `Blocked` 时，表现层必须立即隐藏水流。
- `PourFX` / `PourFxView` 只能读取提交结果中的源点、目标点、颜色和移动量，不得修改 `BottleData`、`GameState` 或倒水计划。
- 水位过渡可以使用表现层临时快照，但真实状态仍以数据层为准。
- 表现层临时快照不得参与规则判断，不得替代 `GameState`。
- 瓶内水层应通过裁剪区域或等效实现限制在瓶身内部，问号黑色层也必须受同一内部区域约束。
- 水层几何应连续贴合，避免层与层之间出现固定空隙。
- 顶部水面可使用轻微波浪，但不得影响层数、颜色和问号规则。
- 非法倒水反馈、自动收集、胜利弹窗和重开流程必须保持原行为。

## 点击交互状态机

建议使用简单状态机管理点击：

| 状态 | 含义 |
| --- | --- |
| Idle | 没有选中任何瓶子 |
| BottleSelected | 已选中一个源瓶 |
| Resolving | 正在执行倒水或反馈，短暂锁输入 |
| Win | 游戏胜利，停止水瓶输入 |

第一版可用 `SelectedBottleId` 和 `IsGameOver` 实现简化状态，但行为必须满足：

- Idle：点击非空、未收集瓶子后选中它。
- Idle：点击空瓶不应选为源瓶。
- BottleSelected：点击同一个瓶子取消选中。
- BottleSelected：点击另一个瓶子尝试倒水。
- Resolving：忽略连点，避免状态错乱。
- Win：忽略水瓶点击，只允许重开。

## 倒水规则实现原则

倒水必须满足：

- 源瓶非空。
- 源瓶和目标瓶不是同一个。
- 源瓶和目标瓶都未被收集。
- 目标瓶未满。
- 源瓶顶部层已揭示。
- 目标瓶为空，或目标瓶顶部真实颜色等于源瓶顶部真实颜色。

计算本次倒出层数时，只统计源瓶顶部已揭示的连续同色层。

实际倒入层数：

```text
min(源瓶顶部已揭示连续同色层数, 目标瓶剩余容量)
```

倒入目标瓶的新水层必须设为已揭示，因为玩家刚刚看到它被倒进去。

## 问号层实现原则

- 数据层中每层水都提前保存真实颜色。
- `IsRevealed` 控制该层是否显示真实颜色。
- 初始每个非空瓶只揭示当前顶部层。
- 成功倒水后，只尝试揭示源瓶新的顶部层。
- 新揭示层不参与本次已经生成的 `PourPlan`。
- 已揭示层不能重新变回问号。

## 自动收集实现原则

收集条件：

- 水瓶未被收集。
- 水瓶层数等于容量。
- 所有层真实颜色相同。

收集后：

- `BottleData.IsCollected = true`。
- 对应颜色 `BagData/FlowerPotData.CollectedCount` 增加。
- 水瓶视图隐藏或播放收集反馈。
- 该水瓶不再可点击，也不能再参与倒水。

建议每次成功倒水后检查所有水瓶。第一版只有 6 个水瓶，全量检查最简单稳定。

## 第二阶段执行规则

第二阶段当前正式执行顺序：

1. `main.tscn` 仍作为总入口和流程容器，启动后首先显示 `HomeGarden`。
2. `HomeGarden` 本次只保留“开始游戏”入口；“选择关卡”按钮应隐藏并禁用，但不从场景中删除。
3. 点击“开始游戏”时，如果存在未完成 `PendingPlanting`，必须停留在 `HomeGarden` 并提示“请先完成本次种植或追加”。
4. 无待种植奖励时，点击“开始游戏”进入 `FlowerSelect`。
5. `FlowerSelect` 固定显示 6 个花格：`pink_rose`、`yellow_rose`、`lavender` 为开放花；`flower_04`、`flower_05`、`flower_06` 为待开放灰态占位。
6. 点击待开放花只提示“该花将在后续版本开放”，不得进入 `LevelSelect`，不得猜测真实花名。
7. 如果开放花已出现在 7 个不同主页位置中，该花在 `FlowerSelect` 中灰态；点击提示“该花已种满，请选择其他花”，不得进入 `LevelSelect`。
8. 选择开放且未满的花后进入 `LevelSelect`。
9. `LevelSelect` 按所选花显示 7 个临时外层关卡；每个花的进度互相独立。
10. 第 1 关默认可玩；已通关关卡灰态 / 锁定不可重复进入；当前可玩关卡正常可点；未解锁关卡灰态 / 锁定不可点。
11. 进入任意可玩关后加载现有 `GameScene.tscn`，实际关卡内容暂时复用当前固定第一关，不实现真实 21 套不同数据。
12. `GameScene` 通关只发出外层完成信号，不直接写主页花园状态；`MainFlowController` 记录所选花当前关通关并解锁下一关。
13. 通关后生成所选花的种子 x1 + 药剂 x1，并回到 `HomeGarden` 的 `PendingPlanting` 状态；不进入旧 `RewardFlower` 四选一页面。
14. `PendingPlanting` 状态下，空花位和不包含本次奖励花的已有花位显示数字圆圈；已包含本次奖励花的花位不显示数字圆圈。
15. 只有点击数字圆圈按钮的圆形区域才触发种植或追加；点击背景、花图、slot 父节点、大范围透明热区或圆圈矩形外角不得触发，也不得清除 `PendingPlanting`。
16. 种植 / 追加成功后，同时消耗本次奖励的种子 x1 + 药剂 x1，清除 `PendingPlanting`，刷新主页，允许再次开始游戏。

第二阶段代码实现边界：

- `RunSessionState` 或等价外层状态类只保存运行期数据：所选花、所选关、每花已通关数量、`PendingPlantingFlowerId`、种子 / 药剂临时标记、`slot -> flower_id 集合 / batch`。
- `RunSessionState` 不保存图片路径、节点路径、Godot 节点引用或本地存档路径。
- `HomeGardenView` 只负责显示花位组合、显示可操作数字圆圈、上报圆圈点击和播放临时反馈；不保存唯一真实状态。
- `FlowerSelectView` 只显示花选项和提示，不直接写主页花位。
- `LevelSelectView` 只显示所选花的 7 个关卡及其可玩状态，不生成或修改倒水关卡数据。
- `MainFlowController` 负责 `HomeGarden -> FlowerSelect -> LevelSelect -> GameScene -> HomeGarden` 的外层切换、奖励生成和种植状态提交。
- `GameScene` / `GameManager` 只负责倒水关卡内部流程；通关后通过信号交给外层。
- `PourSystem` 不处理选花、关卡进度、奖励、种植或主页流程。
- 不修改 `BottleData`、`WaterLayer`、`PourPlan`、`PourResult` 的核心语义，除非有单独倒水规则任务。
- `RewardFlower*` 文件可保留为历史遗留，但不得作为当前正式流程入口。
- `BagSystem`、`BagData`、`BagSlotView` 不在本次重命名；历史命名需继续在文档中说明。
- 本次不实现 `SaveSystem`，不写本地文件。

组合素材执行规则：

- 长期组合素材路径为 `res://assets/flowers/combinations/{combo_key}/home_slots/{combo_key}_slot_01.png` 到 `slot_07.png`。
- 组合 key 按开放花顺序稳定排序：`pink_rose -> yellow_rose -> lavender`。
- 单花也是组合的一种；当前可继续使用既有 `res://assets/flowers/{flower_id}/home_slots/` 作为单花组合入口。
- 多花组合素材缺失时必须显示可识别占位，例如“组合素材待补”，不得崩溃，也不得把多个单花素材临时叠加为正式表现。

第二阶段验收标准：

- 游戏启动后首先显示 `HomeGarden`。
- `HomeGarden` 的“选择关卡”按钮隐藏且禁用，“开始游戏”仍可用。
- “开始游戏”进入 `FlowerSelect`；若 `PendingPlanting` 未完成，停留主页并提示。
- `FlowerSelect` 显示 6 格，只有 `pink_rose`、`yellow_rose`、`lavender` 可进入 `LevelSelect`。
- 点击 `flower_04` 到 `flower_06` 只提示“该花将在后续版本开放”。
- 所选开放花进入 `LevelSelect` 后显示 7 关；第 1 关默认可玩；已完成和未解锁关不可进入。
- 通关第 1 关后，第 1 关锁定，第 2 关解锁；不同花的进度互相独立。
- 通关后生成对应花的 `PendingPlanting`，不进入 `RewardFlower`。
- 空位可种植本次奖励花；已有但不含本次奖励花的位置可追加；已含本次奖励花的位置不可追加。
- 追加后花位保存为排序稳定的组合批次，例如 `pink_rose+yellow_rose`。
- 缺少多花组合素材时显示占位，不崩溃。
- 同一花出现在 7 个不同位置后，`FlowerSelect` 中该花灰态并提示“该花已种满，请选择其他花”。
- 第一版倒水规则、问号层、自动收集、胜利判断、重开功能不被破坏。
- 修改代码后必须运行 `dotnet build`；流程 / UI 改动必须运行 Godot headless 或可行 smoke；真实窗口未验收时必须在 `03_实现文档.md` 标记当前未确认。
